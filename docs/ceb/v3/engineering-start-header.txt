Выполни CEB 3.0 — 100 инженерных заданий. Действует регламент исполнения ceb-execution-1 (ниже); он имеет приоритет над устаревшими инструкциями запуска внутри неизменяемого ZIP. Условия задач и состав входов не меняются. Это практическая работа, не план и не проверка доступности ссылок. Начни решать доступные задания в этом же ответе/сеансе; не заканчивай одним сообщением о недоступности ZIP.
Доставка: ниже указаны точные ссылки и контрольная сумма фиксированного пакета. Сначала проверь вложенные файлы, затем самостоятельно получи архив всеми РАЗУМНО доступными независимыми способами: GitHub Pages → GitHub Raw → GitHub connector (если подключён, используй чтение файла из ветки ceb-inputs по точному пути, не поиск ответов) → Google Drive (если есть указанное зеркало и авторизация) → Яндекс.Диск (если указано зеркало). В сетевой песочнице ошибка DNS/cURL не означает, что браузер, загрузка файла через коннектор или другой хост недоступны. Различай невозможность открыть ZIP как веб-страницу и невозможность получить его байты. Начни с проверки вложения, времени, локального Python и каталога выходов. Для сетевых вызовов, если доступны настройки тайм-аута, используй 15 с на попытку, не более одного повторения временной ошибки. После примерно 120 с суммарной диагностики доставки переходи к встроенным задачам; доступные загрузки продолжай только при необходимости конкретной задачи. Не повторяй бесконечно один и тот же заведомо недоступный способ; не обходи сетевые ограничения, не запрашивай токены/секреты. Для Яндекс.Диска: открой публичную ссылку, скачай engineering-inputs.zip. Если ссылка ведёт на папку, выбери именно этот файл, не ZIP всей папки. Если веб-страница не отдаёт байты и доступен HTTP-клиент, используй публичный API Яндекс.Диска: запрос resources с параметром public_key=точная публичная ссылка; для файла в папке укажи его path; запрос resources/download с public_key и, при необходимости, path возвращает временный href для скачивания. Не подставляй вместо public_key токен доступа. Не считай HTML-страницу, JSON API или архив всей папки входным ZIP. Если инструмента нет, отметь это, попробуй другой доступный канал. Сверяй SHA-256 каждого полученного ZIP, не используй несовпавшие байты. При недоступности ZIP используй точные отдельные входные файлы из указанной папки ветки ceb-inputs (только каталог, инвентарь, шаблон и материалы заданий). Если байты доступны, сравни их хеши с inventory.json; если нет, честно фиксируй ограничение.

При отсутствии среды исполнения выполняй расчёты и доступную часть задач, предоставляй исходники, но не выдумывай созданные файлы и исполненные тесты. ПРОТОКОЛ: для каждого задания ответ, исходные значения, формулы/метод, подстановка, результат с единицами, источники, допущения, фактические проверки (ожидаемое и наблюдаемое), выходные файлы и конкретная причина недочёта. Записывай фактические попытки доставки (канал, действие, результат, код ошибки, число байт, проверка SHA); не выдумывай время, вызовы и файлы. completed — ответ представлен, не правильность; partial — доступная часть; failed — ошибка; blocked — обязательный вход или среда отсутствуют; timeout — исчерпан лимит; not_run — не начато. Не выставляй себе баллы.
Выдай engineering-report.json по приложенному шаблону. Если шаблон недоступен, используй приведённое ниже описание формата и перечень всех 100 ID. Если ограничен объём чата, предоставь фактически решённый блок и checkpoint с номером следующей доступной задачи. Не обещай фоновую работу. При отсутствии возможности создать файл выведи JSON текстом. Приложи реальные выходные файлы в ZIP, если возможно.

РЕЖИМ ИСПОЛНЕНИЯ. Не ограничивайся планом, не ожидай одобрения между задачами, не обещай последующую работу в фоне. Сохраняй атомарно после КАЖДОЙ задачи; после каждых пяти записанных задач либо примерно 2 минут работы, если раньше, сообщай короткий прогресс: закончено, частично, ошибка, блок, не начато, текущий/следующий номер, измеренное время, путь checkpoint. Сообщение не должно прерывать дальнейшее выполнение, если среда позволяет продолжать. Не отправляй пустой финальный ответ. Если платформа принудительно завершает сеанс, выдай последний сохранённый отчёт, ZIP доступных файлов, точный следующий номер и команду возобновления с тем же run_id. Не обещай автоматическое продолжение, если оно недоступно.
ВРЕМЯ. Перед началом каждого задания зафиксируй реальное начало (Python time.monotonic_ns/perf_counter), сразу после сохранения ответа и проверок — конец. Время wall_seconds включает анализ, вычисления, создание и проверку артефактов данной задачи. Не запускай общий таймер на несколько задач с последующим делением. При последовательном режиме сумма измеренных задач = timing.solve_seconds (если измерена только часть, прямо укажи покрытие). Доставка, подготовка, финальная валидация/упаковка и полное внешнее время отдельно; не приравнивай сумму задач к общему времени сеанса. Внешний таймер предпочтителен для сравнения разных моделей. Если доступна только локальная шкала monotonic, timing.source="agent_monotonic"; если нет таймера или шкала изменилась, только соответствующее время null с объяснением, НЕ 0 и НЕ оценка на глаз. Не оставляй времена null при доступном таймере. Не выдавай локально измеренное время за независимое. Для режима исполнения с инструментами используй приложенный ниже стандартный Python ledger engineering-runner.py, либо эквивалент с журналом начала/конца каждой задачи. Наличие часов не даёт возможности измерить уже завершённые задачи задним числом.
